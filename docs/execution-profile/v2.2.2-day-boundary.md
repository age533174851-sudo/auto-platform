## 1. HARD DAY BOUNDARY

Exact100X가 관리하는 전날 포지션은 **매일 08:59 KST에 종료 절차를
시작한다.** 수익·손실 크기와 무관하다.

`+20%` · `+100%` · `+500%` · `+600%` · `-20%` · `-80%` — 전부
`DAY_BOUNDARY` 대상이다.

**단, 소유권이 확인되지 않은 포지션은 닫지 않는다.** 수동 포지션이나
Exact100X 소유가 증명되지 않은 자리까지 임의로 정리한다는 뜻이 아니다.
이건 이 저장소의 기존 규율과 같다 — `symbol만 보고 주문 소유권을
판단하지 않는다`.

## 2. EXIT REASON

`DAY_BOUNDARY_EXIT`은 아래와 **별도의** 사유다:

`TAKE_PROFIT` · `STOP` · `STALE_EXIT` · `STRATEGIC_LIQUIDATION` ·
`SYSTEM_FAULT_EXIT` · `SYSTEM_FAULT_LIQUIDATION` · `MANUAL_CLOSE`

새 canonical reason:

```
DAY_BOUNDARY_EXIT      종료 절차를 시작했다
DAY_BOUNDARY_CLOSED    flat을 확인했다
```

둘을 하나로 합치지 않는다. 시작과 확인은 다른 사실이다.

## 3. CLOSE SEMANTICS

**08:59가 됐다고 DB에서 CLOSED로 바꾸지 않는다.**

```
AUTHORITY CHECK
→ close-mode safety
→ exchange reduce-only close
→ response classification
→ venue position reread
→ flat verification
→ DAY_BOUNDARY_CLOSED
```

```
ORDER SUBMITTED != CLOSED
ORDER ACCEPTED  != CLOSED
```

재조회가 실패하거나 결과가 모호하면 `EXCHANGE_UNKNOWN` /
`RECONCILING`으로 둔다. **flat을 추측하지 않는다.**

## 4. NEW SESSION ENTRY GATE

09:00 KST부터 새 Exact100X 세션이 시작된다. 그러나 전날 포지션이 아직
flat 확인되지 않았다면:

```
CAN_AUTO_ENTER = FALSE

PREVIOUS_SESSION_FLAT_VERIFIED
  is required for
NEW_SESSION_AUTO_ENTRY
```

전날 포지션이 `UNKNOWN` / `EXITING` / `RECONCILING`이면 새 포지션을
**겹쳐 열지 않는다.**

## 5. ENTRY WINDOW

신규 진입 후보 평가 기본 구간: **09:00:00 ~ 09:30:00 KST**

이 구간은 "09:00에 무조건 진입한다"는 뜻이 **아니다.** 조건을 만족하는
후보만 진입하고, **진입하지 않는 것도 정상 결과다.**

## 6. INTRADAY EXIT PHILOSOPHY

08:59 hard boundary **이전에는** 단순히 수익이 크다는 이유로 winner를
닫지 않는다. `+100%` · `+300%` · `+500%` · `+600%` 같은 절대 ROE는
그 자체로 profit exit trigger가 아니다.

기본 철학:

- downside는 isolated margin으로 제한
- invalid trade는 −100% 이전에도 줄일 수 있음
- profitable trend는 right-tail을 최대한 보존
- premature profit truncation 금지
- MFE capture 개선
- excessive MFE giveback 감소

## 7. PRECEDENCE

```
SYSTEM / OWNERSHIP SAFETY
  >  DAY BOUNDARY
  >  LIQUIDATION / EMERGENCY RISK
  >  ADAPTIVE EXIT POLICY
  >  NORMAL RUNNER MANAGEMENT
```

08:59에서는 adaptive runner 판단보다 `DAY_BOUNDARY`가 우선한다.
**단, 시스템 안전 규칙을 우회해서 닫지는 않는다** — 맨 위가 SAFETY인
이유가 그것이다. 임차(fence)를 잃었거나 종료 모드를 확인하지 못했으면
08:59라도 보내지 않는다.

## 8. REQUIRED TELEMETRY

최소:

| 칸 | 뜻 |
| --- | --- |
| `intended_boundary_at` | 08:59로 계획된 시각 |
| `exit_started_at` | 실제로 절차를 시작한 시각 |
| `close_attempted` | 거래소에 보냈는가 |
| `close_accepted` | 거래소가 받았는가 (**모르면 null**) |
| `flat_verified` | 재조회로 0을 확인했는가 (**못 읽으면 null**) |
| `flat_verified_at` | 확인 시각 |
| `reconcile_state` | 대조 상태 |
| `exit_reason` | `DAY_BOUNDARY_EXIT` 등 |
| venue response/error | 거래소 응답·오류 |
| remaining position after reread | 재조회 후 잔여 |

가능하면 추가:

- 08:59 시점 PnL
- boundary 이전 MFE
- realized PnL
- boundary가 유발한 MFE giveback

마지막 값은 **"08:59 boundary 자체가 장기 expectancy를 훼손하는가"**를
나중에 검증할 때 쓴다.

## 9. BACKTEST / SIMULATION

PR4 / PR4.5에서 **동일 entry cohort로 두 정책을 별도 재현**한다:

```
A. no day boundary
B. 08:59 hard boundary
```

측정: Net PnL · Expectancy · Profit Factor · Max Drawdown ·
Liquidation Rate · Tail Contribution · Median Winner ·
Top winner contribution · MFE Capture · Boundary Giveback ·
Overnight exposure avoided

08:59 정책은 **운영 계약으로 적용하되, 그 경제적 효과도 계속 계측한다.**

### 이 규칙이 스스로 예외임을 적어 둔다

08:59 때문에 `+600%` 승자를 끊는 것은 "winner를 오래 살린다"는 §6
원칙의 **유일한 명시적 시간 예외**다. 그래서 `Boundary Giveback`을
따로 본다.

08:59에 `+400%`로 닫았는데 그 뒤 `+900%`까지 간 사례가 **반복되면**,
감으로 바꾸지 않고 **08:59 룰 자체를 다시 실험 대상으로 올린다.**
그 판단의 근거는 §8의 telemetry와 §9의 A/B 재현이다.

### 구현 시 주의

- §4의 진입 게이트는 PR-E와 **하나의 게이트**로 만든다. `CAN_AUTO_ENTER`가
  두 곳에서 다르게 계산되면 이 저장소가 이름 붙인 2번 고장이다.
- §1의 08:59는 **사용자 확정 운영 규칙**이다. `lifecyclePolicy`의
  6h/24h는 `LIFECYCLE_TESTNET_V1` 출처의 검증용 값이고, 이 둘을 같은
  것으로 합치지 않는다. 출처가 다르면 표시도 달라야 한다.
- §3은 이미 `lifecycleAction`이 갖고 있다. 08:59 경로가 그것을 **재사용**해야
  하고, 종료 순서를 다시 쓰면 안 된다.
