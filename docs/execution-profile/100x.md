# 전용 100배 (`MAX_LEV_100X` + `EXACT_100X`)

> 이 프로필이 보장하는 것은 수익이 아니라 **일치**다. 화면에 100배라고
> 적혀 있으면 거래소에도 100배가 걸려 있고, 아니면 주문이 나가지 않는다.

## 레거시 "상한 100배"와 무엇이 다른가

|  | 레거시 `levCap = 100` | 전용 100배 |
|---|---|---|
| 100의 뜻 | **상한** — 여기까지 허용 | **요청값** — 정확히 이것 |
| 실제 배율 | 손절 거리에서 역산 후 상한에서 clamp | 항상 100 |
| 되읽기 | 설정 응답의 `success`만 확인 | 독립 되읽기 후 `MATCH`만 통과 |
| 75배로 잡히면 | 통과 (위험이 줄었으니까) | **주문 안 함** (`VENUE_CAPPED`) |
| 마진 모드 | 계좌 설정대로 | **되읽어 isolated 확인.** cross·모름이면 안 나감 |
| 손절 | 고정 손절 필수 | **고정 손절 없음** (`NO_FIXED_SL`) |
| 수량 근거 | 허용손실 ÷ 손절거리 | 잔고 × **예약에 입력한** 배정 비율 × 100 ÷ 기준가 |

레거시는 화면에 "100배"라고 적혀 있어도 실제 배율은 손절 거리에서 역산돼
상한에서 잘렸다 — 적힌 것과 나가는 것이 달랐다. 두 개념이 한 화면에 있으면
사용자는 상한을 고른 것을 전용으로 읽는다. 그래서 이름 규칙도 일부러 다르게
했다(`<시간축>_<위험등급>_LEV`가 아니다).

**기존 세 프로필(`SCALP_HIGH_LEV` · `SWING_LOW_LEV` · `DAILY_HIGH_LEV`)의
값과 마진 모드 의미는 한 글자도 바뀌지 않았다.** 실행 중인 예약·포지션의
의미는 그대로다(시험이 고정한다).

## 조합이 하나뿐인 이유

```
MAX_LEV_100X  ×  EXACT_100X   ← 이것만 해석된다
MAX_LEV_100X  ×  STABILIZE    → PROFILE_PRESET_MISMATCH
MAX_LEV_100X  ×  RESEARCH     → PROFILE_PRESET_MISMATCH
SCALP/SWING/DAILY × EXACT_100X → PROFILE_PRESET_MISMATCH
```

프리셋은 원래 "같은 프로필의 값을 좁히거나 넓히는 축"이다. 전용 100배는 그
축 위에 없다 — 어느 프리셋이든 100배여야 하는데, 그러면 프리셋 선택이 아무
뜻이 없으면서 화면에는 "안정화를 골랐다"고 남는다. 사용자는 배율이 낮아졌다고
읽는다.

**양방향으로 막는다.** 한쪽만 막으면 `SCALP_HIGH_LEV + EXACT_100X`가 통과해서
"전용 100배 프리셋인데 25배"가 저장된다.

막힌 조합은 지문에 `UNRESOLVED`로 **남는다.** 빼 버리면 나중에 그 조합이
열려도 지문이 그대로라 버전 상승을 요구하지 못한다 — 허용 범위가 조용히
넓어진다.

## 계약 v2 — 정책 두 축

```
stopPolicy   = FIXED_SL | NO_FIXED_SL
sizingPolicy = STOP_RISK | MARGIN_ALLOCATION

기존 3개     = FIXED_SL    + STOP_RISK
MAX_LEV_100X = NO_FIXED_SL + MARGIN_ALLOCATION
```

**배정 비율(%)은 계약이 아니다.** 그 값은 프로필 상수가 아니라 예약마다
사용자가 명시하는 값이다. 계약에 넣으면 사용자가 나중에 비율을 입력해도
계약은 계속 옛 값을 가리킨다 — 값이 두 곳에 생기고 실행은 옛 쪽을 읽는
구조가 된다. 그래서 `autotrade_schedules.margin_allocation_pct`(`079`)에 있고,
계약에는 **그 값을 쓴다는 사실**만 남는다.

화면의 `marginPct`(기본값 `'10'`)를 여기로 상속하지 않는다. 그쪽은 손절 거리
기반 사이징의 증거금 상한이고, 사용자가 고른 적 없어도 값이 들어간다.

## 배율 — 어디가 고장나 있었나

공통 `futuresPlaceOrder`는 이미 되읽기 판정을 탄다. Worker는 그 경로를 쓴다.

```
futuresPlaceOrder → futuresApplyLeverage
                    → futuresSetLeverage        (설정)
                    → futuresPositionRisk       (독립 되읽기)
                    → leverageVerdict           (MATCH만 ok)
```

Web `orderExecutor`만 그 경로를 타지 않았다. 정확히 말하면 "되읽기가 없었다"가
아니다 — `setFuturesLeverage`·`setLeverageGateFutures`는 안에서 되읽는다.
문제는 **거래소가 요청보다 낮게 잡은 경우에도 `success: true`를 돌려준다**는
것이다.

```
binanceFutures.setFuturesLeverage  "요청 100배 / 실제 75배 — 거래소가 낮췄습니다"  → success: true
gateFutures.setLeverageGateFutures "요청 100배 / 실제 75배 — 거래소가 조정했습니다" → success: true
```

위험이 줄어드는 방향이라 일반 전략에는 맞는 판단이다. 하지만 100배 크기로
정해 놓고 75배로 나가면 **사용자가 검증한 것과 다른 전략이 도는 것**이다.
이제 두 경로 다 `leverageVerdict`가 판정한다.

Gate는 `futuresPositionRisk`가 `gatePositionToRisk(...).leverage`를 돌려주므로
Binance-only 제한을 두지 않았다. 다만 **포지션이 없는 신규 진입 직전에도
Gate가 그 값을 주는지는 실계좌로 확인되지 않았다**(EVIDENCE_GAP) — 저장소
전반의 Gate 경로가 같은 상태다. 회귀는 가짜 어댑터로만 했다.

## 마진 모드 — ISOLATED 전용 (사용자 확정 정책)

cross까지 열면 같은 이름 아래에서 담보 범위·가용 잔고의 뜻·청산과 복구의
의미가 달라져 **사실상 다른 전략 둘**이 된다. 크기를 `가용 잔고 × 명시 배정
비율 × 배율`로 고정하는 이 계약에서는 격리여야 그 식이 한 가지 뜻을 갖는다.
Gate는 교차를 leverage 0으로 표현해서 되읽기가 null이 되는 경계도 있다.

Cross 100배가 필요해지면 이 프로필의 뜻을 바꾸지 말고 **별도 프로필/계약**으로
만든다.

## 진입 순서 — 무엇을 먼저 물어보는가

`engine/entry100x.ts`가 그 순서를 갖는다. 라우트에 인라인으로 쓰면 가장 중요한
순서가 시험되지 않는 자리에 남고, 다른 라우트가 복제하게 된다. **의존을
주입받으므로 가짜 어댑터로 전 구간을 회귀할 수 있다.**

```
① 마진 모드 되읽기      cross·모름 → 멈춤
② 배율 걸고 되읽기      요청값과 다르면 → 멈춤
③ 가용 잔고             못 읽으면 → 멈춤 (0으로 눕히지 않는다)
④ 기준가                서버가 읽은 값. 신호의 진입가가 아니다
⑤ planSize100x          잔고 × 배정 % × 배율 ÷ 기준가
⑥ 거래소 수량 규격      못 맞추면 → 멈춤
⑦ 필요 증거금 재검증    다듬느라 배정을 넘으면 → 멈춤
```

①이 ②보다 앞인 이유: 교차 계좌에 배율부터 걸면 **막을 주문을 위해 계좌
설정을 먼저 바꾸는 것**이 된다. 확인이 먼저다. 시험과 검사기가 이 순서를
직접 확인한다(교차일 때 `applyLeverage`가 불리면 실패).

⑦이 필요한 이유: 거래소 수량 단위는 올림이 될 수 있다. 0.2가 0.3이 되면
필요 증거금이 배정보다 커지고, 그 차이는 사용자가 허락한 적이 없다.

각 단계는 **다른 코드로** 막는다 — `MARGIN_MODE_UNKNOWN` / `MARGIN_MODE_NOT_ISOLATED` /
`LEVERAGE_NOT_EXACT` / `SIZING_BLOCKED` / `QUANTIZE_FAILED` / `MARGIN_EXCEEDED`.
다른 검사가 우연히 막아 주면 사용자에게 잘못된 원인이 보인다.

## 고정 손절 없음 — 숫자가 아니라 정책

`stopLossPct: 0.5` 같은 숫자를 남겨 두면 그 값이 사이징의 분모나 복구 경로의
손절가로 되살아난다. 그래서 `stopLossPct`는 `null`이고 정책이 따로 있다.

lifecycle 전체에서 고정 손절이 다시 걸리지 않게 네 자리를 막았다.

| 자리 | 무엇을 하는가 |
|---|---|
| 진입 `orderExecutor` | `protectionPolicy`를 `NONE`으로 **덮는다.** 손절가가 함께 오면 모순이라 주문 안 함 |
| 복구 `stopReattachVerdict` | **값보다 정책을 먼저 본다.** `078`의 `live_orders.stop_policy`가 근거 |
| 청산 감시 `lifecycleDecide` | `NO_FIXED_STOP`으로 멈춘다. `planTrail`의 1R 계산 실패에 기대지 않는다 |
| 워커 `SET_TPSL` | `stopPolicy = NO_FIXED_SL`이면 손절을 거부한다 (익절은 막지 않는다) |

체크리스트에서는 세 항목이 **목록에서 빠진다**(pass 아님):
`STOP_ATTACHED` · `LIQUIDATION_DISTANCE` · `PROTECTIVE_ORDER`.
손절과 무관한 13개는 그대로 남고 시험이 고정한다. 사람이 누르는
`noStopAcknowledged`는 재사용하지 않는다. global `LEVERAGE`의 `blocking:false`도
건드리지 않았다.

> **SET_TPSL 생산자는 아직 없다.** `enqueueJob`을 부르는 제품 코드가 0건이라
> 그 잡을 만드는 곳이 없다. 그래서 "생산자가 `stopPolicy`를 싣는지"는 지금
> 증명할 대상이 아니다. 대신 **생산자가 생기는 날 CI가 요구하도록** 규칙만
> 걸어 뒀다 — `action: 'SET_TPSL'`을 만드는 파일에 `stopPolicy`가 없으면 실패.

## 켜기 — TESTNET 조합 하나만

`execution/dormantGate.ts`의 `OPEN_COMBOS` 하나가 정본이고, L3(PATCH 켜기)와
L4(실행 직전)와 진입 라우트가 전부 그것을 읽는다. DB(L1)는 `080`이 같은 조합을
제약으로 적는다 — 워커가 웹 평가기를 빌드 시점에 번들하므로 배포가 엇갈리는
창은 코드 층만으로 못 막는다.

```
열림: MAX_LEV_100X + EXACT_100X + 계약 v2 + TESTNET + 배정 비율 입력됨
```

닫힌 것과 그 이유:

- **같은 조합의 LIVE** — 고정 손절을 대신할 자동 종료 권한이 실제로 배선돼
  있다는 증거가 없다. `exitLifecycle.lifecycleDecide`에서 손절 없이 도는 것은
  `TIME_EXIT`(최대 보유 시간) 하나뿐이고, 트레일링·본전이동은 `planTrail`이
  `initialStop > 0`을 요구해 아예 돌지 않는다. 게다가 `lifecyclePolicyOf`는
  **전략 id**로만 조회해서 이 실행 프로필과 연결이 없다.
  **이 조건을 통과시키려고 임의의 exit 문턱을 새로 만들지 않는다.**
- **기존 세 프로필의 명시적 선택** — 실행기가 그 계약대로 실행하지 않는다.
  저장은 되지만 켜지지 않는다.
- **배정 비율이 비어 있는 예약** — 크기를 만들 수 없다. 켜 두면 켜져 있는데
  아무것도 안 하는 상태가 되고, 사용자는 도는 줄 안다.

L2(저장 시 `enabled:false` 강제)는 그대로다. 설정을 바꾸는 것과 켜는 것은
다른 행위다.

## UI

`AutotradeControl`에 전용 블록이 있다. 저장(꺼진 채로)과 켜기가 나뉘어 있고,
배정 비율 칸은 **기본값이 없다.**

표시는 **저장된 예약에서만** 파생한다 — 입력칸에서 파생하면 저장하지도 않은
값이 "전용 100배로 도는 중"처럼 보인다. 장식용 배지가 생기는 정확한 경로다.

```
UI 선택 → execution_profile_id / preset_id / contract_version / margin_allocation_pct
        → resolveExecutionProfile (조합·버전 정확 일치만)
        → ExecutionContract (stopPolicy · sizingPolicy)
        → planEntry100x (마진모드 · 배율 되읽기 · 잔고 · 기준가)
        → executeOrder (stopPolicy → live_orders.stop_policy)
```

## 모의 성적표에서 빠진 이유

`simModel`은 고정 익절·손절 한 쌍에서 무우위 승률을 낸다. 손절이 없으면
`noEdgeWinRate`가 0.5를 돌려주는데, 그건 **관측이 아니라 자리 채우기**다.
그 숫자로 성적표를 그리면 근거 없는 기대값이 화면에 뜬다.

`simulatableProfiles()`가 `FIXED_SL` 프로필만 돌려준다.
**모의를 못 하는 것과 실행을 못 하는 것은 다른 얘기다.**

## 계약 버전 1 → 2

`CONTRACT_FIELDS`에 `stopPolicy`·`sizingPolicy`가 늘어 지문이 바뀌었고,
`check-execution-profile.mjs`가 버전 상승을 요구했다.

- 세 칸이 all-null인 기존 예약 → `kind: 'none'` → **영향 0**
- `execution_contract_version = 1`이 저장된 예약 → `VERSION_MISMATCH`,
  자동 승격 없음, 사용자가 다시 저장해야 함
- `077` 적용 전이라 그런 행은 **현재 0건**이다

## 검사기

`scripts/check-100x-contract.mjs` (CI 배선)

값을 소스에서 regex로 읽지 않는다 — 프로필 리터럴만 보면 `applyPreset`이 얹는
override를 놓친다. **정본을 컴파일해서 실제로 부르고** 결과를 본다. 리터럴과
합쳐진 계약이 갈리는 것도 잡는다.

`planEntry100x`도 **가짜 어댑터로 실제 돌려서** 각 단계가 맞는 코드로 막는지
본다. 막았는지만 보면 부족하다 — 검사를 지워도 뒤쪽 검사가 우연히 막아 주는
경우가 있고, 그때 사용자에게는 잘못된 원인이 보인다.

그리고 **production 체인이 닫혀 있는지**를 센다. `planEntry100x`·
`stopPolicyOfContract`·`sizingPolicyOfContract`를 제품 코드에서 부르는 곳이
0건이면 실패한다 — 시험과 검사기만 부르면 계약은 초록인데 실제 주문은 그
경로를 타지 않는다. DB 제약(`080`)과 코드 표(`OPEN_COMBOS`)가 갈리는 것도
잡는다.

### 곁들여 고친 검사기 하나

`check-db-columns.mjs`가 **한 문장의 여러 `ADD COLUMN` 중 첫 개만** 읽고
있었다. 그래서 `077`이 더한 세 칸 중 둘(`execution_preset_id`,
`execution_contract_version`)은 이 검사기가 존재를 모르는 상태였고, 그 칸을
`select`하는 코드가 "없는 칸"으로 잘못 잡혔다. 문장을 통째로 떼어 그 안의
`ADD COLUMN`을 전부 훑도록 고쳤다.
