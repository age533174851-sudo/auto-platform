# 전용 100배 (`MAX_LEV_100X`)

> 이 프로필이 보장하는 것은 수익이 아니라 **일치**다. 화면에 100배라고
> 적혀 있으면 거래소에도 100배가 걸려 있고, 아니면 주문이 나가지 않는다.

## 레거시 "상한 100배"와 무엇이 다른가

|  | 레거시 `levCap = 100` | 전용 `MAX_LEV_100X` |
|---|---|---|
| 100의 뜻 | **상한** — 여기까지 허용 | **요청값** — 정확히 이것 |
| 실제 배율 | 손절 거리에서 역산 후 상한에서 clamp | 항상 100 |
| 되읽기 | 설정 응답의 `success`만 확인 | `futuresPositionRisk` 독립 되읽기 후 `MATCH`만 통과 |
| 75배로 잡히면 | 통과 (위험이 줄었으니까) | **주문 안 함** (`VENUE_CAPPED`) |
| 손절 | 고정 손절 필수 | **고정 손절 없음** (`NO_FIXED_SL`) |
| 수량 근거 | 허용손실 ÷ 손절거리 | 가용 잔고 × 배정 비율 × 100배 ÷ 기준가 |
| 도달 조건 | 손절 0.26% 안쪽 — 사실상 선택 안 됨 | 계약이 요구 |

레거시에서 화면에 "100배"라고 적혀 있어도 실제로는 75배가 나갔다.
두 개념이 한 화면에 있으면 사용자는 상한을 고른 것을 전용으로 읽는다 —
그래서 이름 규칙도 일부러 다르게 했다(`<시간축>_<위험등급>_LEV`가 아니다).

**기존 세 프로필(`SCALP_HIGH_LEV` · `SWING_LOW_LEV` · `DAILY_HIGH_LEV`)의
값은 한 글자도 바뀌지 않았다.** 실행 중인 예약·포지션의 의미는 그대로다.

## 배율 — 어디가 고장나 있었나

공통 `futuresPlaceOrder`는 이미 되읽기 판정을 탄다. Worker는 그 경로를 쓴다.

```
futuresPlaceOrder → futuresApplyLeverage
                    → futuresSetLeverage        (설정)
                    → futuresPositionRisk       (독립 되읽기)
                    → leverageVerdict           (MATCH만 ok)
```

Web `orderExecutor`만 그 경로를 타지 않았다. 그런데 정확히 말하면
"되읽기가 없었다"가 아니다 — `setFuturesLeverage`·`setLeverageGateFutures`는
안에서 되읽는다. 문제는 **거래소가 요청보다 낮게 잡은 경우에도
`success: true`를 돌려준다**는 것이다.

```
binanceFutures.setFuturesLeverage  "요청 100배 / 실제 75배 — 거래소가 낮췄습니다"  → success: true
gateFutures.setLeverageGateFutures "요청 100배 / 실제 75배 — 거래소가 조정했습니다" → success: true
```

위험이 줄어드는 방향이라 일반 전략에는 맞는 판단이다. 하지만 100배 크기로
정해 놓고 75배로 나가면 **사용자가 검증한 것과 다른 전략이 도는 것**이다.
이제 두 경로 다 `leverageVerdict`가 판정한다.

Gate는 `futuresPositionRisk`가 `gatePositionToRisk(...).leverage`를 돌려주므로
Binance-only 제한을 두지 않았다. 다만 **포지션이 없는 신규 진입 직전에도
Gate가 그 값을 주는지는 실계좌로 확인되지 않았다**(EVIDENCE_GAP) — 저장소
전반의 Gate 경로가 같은 상태다. 회귀는 격리 판정 함수로만 했다.

## 고정 손절 없음 — 숫자가 아니라 정책

`stopLossPct: 0.5` 같은 숫자를 남겨 두면 그 값이 사이징의 분모나 복구
경로의 손절가로 되살아난다. 그래서 계약에 축을 하나 더 뒀다.

```
stopPolicy = FIXED_SL | NO_FIXED_SL
MAX_LEV_100X → NO_FIXED_SL, stopLossPct = null
```

lifecycle 전체에서 고정 손절이 다시 걸리지 않게 네 자리를 막았다.

| 자리 | 무엇을 하는가 |
|---|---|
| 진입 `orderExecutor` | `protectionPolicy`를 `NONE`으로 **덮는다.** 손절가가 함께 오면 모순이므로 주문하지 않는다 |
| 복구 `stopReattachVerdict` | **값보다 정책을 먼저 본다.** `078`의 `live_orders.stop_policy`가 근거 |
| 청산 감시 `lifecycleDecide` | `NO_FIXED_STOP`으로 멈춘다. `planTrail`의 1R 계산 실패에 기대지 않는다 |
| 워커 `SET_TPSL` | `stopPolicy = NO_FIXED_SL`이면 손절을 거부한다 (익절은 막지 않는다) |

체크리스트에서는 세 항목이 **목록에서 빠진다**(pass 아님):
`STOP_ATTACHED` · `LIQUIDATION_DISTANCE` · `PROTECTIVE_ORDER`.
"손절이 붙어 있음 ✓"는 없는 것을 있다고 적는 것이다.
손절과 무관한 13개는 그대로 남고, 시험이 그것을 고정한다.
사람이 누르는 `noStopAcknowledged`는 재사용하지 않는다 — 아무도 누르지
않은 승인이 눌린 것처럼 기록되면 안 된다.

## 크기 — 근거가 없으면 만들지 않는다

`riskManager.planPosition`은 `허용손실 ÷ 손절거리`라 손절이 분모다.
분모를 지어내는 대신 별도 authority를 뒀다(`engine/sizing100x.ts`).

```
배정 증거금 = 가용 잔고 × 배정 비율(%)
목표 명목가 = 배정 증거금 × 100
수량        = 목표 명목가 ÷ 기준가
```

네 입력 중 하나라도 모르면 BLOCK이고, 각각 **다른 코드**로 막는다.

| 상황 | 코드 |
|---|---|
| 되읽은 배율이 100이 아니거나 모름 | `LEVERAGE_NOT_EXACT` |
| 잔고를 못 읽음 | `BALANCE_UNKNOWN` (0이 아니다) |
| 잔고가 0 | `BALANCE_EMPTY` |
| 배정 비율 미지정 | `MARGIN_ALLOCATION_UNSET` |
| 기준가를 못 읽음 | `PRICE_UNKNOWN` |

`marginAllocationPct`는 **아직 정하지 않았다(null)**. 그래서 이 프로필은
지금 반드시 막힌다 — 의도된 상태다. 화면의 기본값 `marginPct='10'`을
여기로 끌어오지 않는다. 그 값은 사용자가 이 프로필을 위해 고른 값이 아니다.

기준가는 **서버가 읽은 마크/기준가**여야 한다. 신호가 들고 온
`entryPrice`를 거래소 관측가처럼 쓰지 않는다.

## 아직 켜지 않는다

`execution/dormantGate.ts`의 `EXECUTABLE_PROFILE_IDS`가 비어 있고,
L3(PATCH 켜기)와 L4(실행 직전)가 **그 목록 하나**를 읽는다.
판단이 두 곳에 있으면 "실행기는 통과시키는데 사용자는 켤 수 없는" 상태가
시험만 초록인 채로 남는다.

여는 조건 둘, 아직 하나도 충족되지 않았다.

**① 고정 손절을 대신할 자동 종료 권한이 배선돼 있지 않다.**

`exitLifecycle.lifecycleDecide`에서 손절 없이 도는 것은 `TIME_EXIT`
(최대 보유 시간) 하나뿐이다. 트레일링·본전이동은 `planTrail`이
`initialStop > 0`을 요구해서 아예 돌지 않는다. 그리고 `lifecyclePolicyOf`는
**전략 id**(`daily-ladder` · `scalp` · `my-original-v1`)로만 조회한다 —
실행 프로필과 연결이 없어서 `MAX_LEV_100X`에는 정책이 없다.

100배의 청산 거리는 대략 0.6~1%다. 4시간 시간 청산은 그 자리를 대신하지
못한다. **임의의 새 exit threshold를 만들어 이 조건을 통과시키지 않는다.**

**② `marginAllocationPct` 값이 정해지지 않았다.**

이 둘이 남아 있는 한 LIVE는 물론 dormant 해제도 하지 않는다.
`077`의 `autotrade_schedules_execution_profile_dormant` 제약은 그대로 둔다.

## 모의 성적표에서 빠진 이유

`simModel`은 고정 익절·손절 한 쌍에서 손익비를 구하고 거기서 무우위 승률을
낸다. 손절이 없으면 `noEdgeWinRate`가 0.5를 돌려주는데, 그건 "반반"이라는
**관측이 아니라 자리 채우기**다. 그 숫자로 성적표를 그리면 근거 없는
기대값이 화면에 뜬다.

`simulatableProfiles()`가 `FIXED_SL` 프로필만 돌려준다.
**모의를 못 하는 것과 실행을 못 하는 것은 다른 얘기다** — 실행 계약은 그대로 있다.

## 계약 버전 1 → 2

`CONTRACT_FIELDS`에 `stopPolicy`·`marginAllocationPct`가 늘어 지문이 바뀌었고,
`check-execution-profile.mjs`가 버전 상승을 요구했다.

- 세 칸이 all-null인 기존 예약 → `kind: 'none'` → **영향 0**
- `execution_contract_version = 1`이 저장된 예약 → `VERSION_MISMATCH`,
  자동 승격 없음, 사용자가 다시 저장해야 함
- `077` 적용 전이라 그런 행은 **현재 0건**이다

## 검사기

`scripts/check-100x-contract.mjs` (CI 배선)

값을 소스에서 regex로 읽지 않는다 — 프로필 리터럴만 보면 `applyPreset`이
얹는 override를 놓친다. **정본을 컴파일해서 실제로 부르고** 결과를 본다.
리터럴과 합쳐진 계약이 갈리는 것도 잡는다(표에 적힌 숫자와 실행이 다른 상태).

배선은 "이름이 있는가"가 아니라 **"옛 판단이 사라졌는가"**까지 본다.
설정 응답의 `success`로 배율을 통과시키는 자리가 남아 있으면 실패다.
막았는지만이 아니라 **어떤 이유로 막았는지**도 고정한다 — 다른 검사가
우연히 막아 주면 사용자에게 잘못된 원인이 보인다.

## UI

이 PR에는 100X 선택 UI가 **없다.** 프로필이 dormant라서, 선택지를 만들면
사용자가 저장은 되는데 켤 수 없는 예약만 만들게 된다. 화면에 100X 배지가
뜨는데 실행은 안 되는 상태가 정확히 이 작업이 없애려는 고장이다.

UI는 dormant를 여는 PR에서 함께 붙인다. 그때 체인은 이렇다:

```
UI 선택 → execution_profile_id / preset_id / contract_version
        → resolveExecutionProfile (정확 일치만)
        → ExecutionContract (stopPolicy · marginAllocationPct)
        → sizing100x / orderExecutor
        → futuresApplyLeverage → observed === 100 (MATCH)
```

화면 표시는 **저장·해석된 identity에서 파생**한다. 로컬 입력 상태에서
파생하면 장식용 배지가 다시 생긴다.
